## 一、全景图：两个阶段，四个环节

RAG 全流程可以概括为 **"两个阶段，四个环节"**：

- **离线阶段（预处理）：** 索引构建
- **在线阶段（推理）：** 召回 → 重排 → 生成

用考试来类比：

> 索引就是考前整理复习资料，建立目录和标签；召回是快速翻书找到相关章节；重排是从找到的内容里挑出最精华的几段；生成就是把检索到的内部数据给AI生成答案。

下面我们逐个环节深挖。

---

## 二、索引 —— 把"书"变成 AI 能查的"目录"

索引是 RAG 的地基。地基不牢，后面全是空中楼阁。

### 1. 文档解析：原始文件 ≠ 模型能吃的数据

你的数据可能躺在 PDF、Word、PPT、Excel、网页里。第一步就是把它们统一转换成纯文本。

这里有几个坑：

- PDF 里的表格解析出来可能是一堆乱码
- 多栏排版的文章，阅读顺序会乱
- 扫描件是图片，需要 OCR

**实战建议：** 针对不同文件类型选不同的解析工具，PDF 用 PyPDF2 或 pdfplumber，Word 用 python-docx。对于复杂的版面，可以考虑开源方案如 Unstructured.io，或者直接用商业 API。

### 2. 数据清洗：别把垃圾喂给模型

解析出的文本里通常充斥着：

- 页眉页脚
- 无意义的换行符
- 特殊字符
- 重复内容

这些都需要清洗掉。这一步看着不起眼，但直接影响后续 embedding 的质量——你把"©2024 公司版权所有"这种噪声也向量化了，它会在语义空间里稀释真正的内容信号。

### 3. 分块（Chunking）：核心中的核心

这是索引环节最重要的决策，没有之一。

为什么不能把整个文档当一块？

- 大模型的上下文窗口再大，也装不下整本书
- embedding 模型对长文本的语义捕捉能力会衰减
- 检索单元太大，匹配的精准度会下降

**分块策略对比：**

| 策略         | 做法                      | 适用场景                 |
| ------------ | ------------------------- | ------------------------ |
| 固定大小分块 | 按 512/1024 个 token 切分 | 通用场景，简单粗暴       |
| 按句子切分   | 按句号、问号等断句        | 对语义完整性要求高的场景 |
| 按段落切分   | 保留自然段落边界          | 文章结构清晰的场景       |
| 递归分块     | 先按段落，太大再按句子    | 兼顾结构与大小控制       |
| 语义分块     | 用模型判断语义转折点      | 追求极致效果，成本较高   |

一个实用的经验法则：**chunk_size 设 512-1024，overlap 设 10%-20%。** 重叠是为了防止关键信息恰好被切在两块边缘导致语义丢失。

### 4. Embedding：把文字变成数学

分好的文本块需要转化成向量——一串浮点数数组，典型的维度是 768、1536 或 4096。

**选 embedding 模型的三个考量：**

- **效果：** 看 MTEB 榜单的检索任务分数
- **语言：** 中文场景优先选 bge-large-zh、m3e 等中文优化过的模型
- **维度：** 维度越高越精准，但存储和检索成本也越高

### 5. 向量存储：建个"知识仓库"

把所有的文本块和它们对应的向量存起来，同时建立索引结构以便快速检索。

**主流向量数据库：** Milvus、Qdrant、Pinecone（云端）、Weaviate、Chroma（轻量）。

**索引类型选择：**

| 索引类型         | 特点                               | 适用场景             |
| ---------------- | ---------------------------------- | -------------------- |
| HNSW             | 检索速度快，构建也快，内存占用适中 | **最常用，首选方案** |
| IVF              | 先聚类再检索，牺牲一点精度换速度   | 百万级以上数据量     |
| Flat（暴力检索） | 最准但最慢                         | 只适合小规模数据     |

## 三、召回 —— 从海量文档里"捞"相关的

用户提一个问题，系统从向量数据库里找出最相关的 N 个文档块。这里说的是向量召回，也是目前 RAG 最主流的召回方式。

### 1. 查询向量化

把用户的问题用**同一个** embedding 模型转成向量。

> **注意：** 必须和索引阶段用的模型一致，否则向量空间不匹配，检索结果毫无意义。

### 2. 相似度计算

在向量空间里找距离最近的 K 个向量。常见的相似度算法：

- **余弦相似度：** 最常用，关注方向而非长度
- **点积：** 关注方向和长度
- **欧氏距离：** 关注绝对距离

大多数向量数据库默认用余弦相似度，没什么特殊需求就用它。

### 3. 多路召回（进阶玩法）

单一向量召回有时候不够稳，尤其是处理"精准匹配"需求时（比如用户问"第三章讲了什么"）。

多路召回指的是同时跑多种检索方式，然后合并结果：

| 召回方式                  | 能力                   | 短板                           |
| ------------------------- | ---------------------- | ------------------------------ |
| 向量召回                  | 语义匹配，泛化能力强   | 专有名词、精确数字可能漏       |
| 关键词召回（BM25/TF-IDF） | 精准匹配专有名词、术语 | 不理解语义，换个说法就匹配不上 |
| SQL 召回                  | 结构化数据直接查数据库 | 只适用于结构化数据             |

多路召回的好处是"两条腿走路"，坏处是合并去重和权重配平需要额外设计。

## 四、重排 —— 把"相关"变成"真正有用"

召回阶段取回了 Top-K（通常是 50-100 个）文档块，但其中很多可能只是"勉强相关"。重排（Rerank）的任务是把这批候选结果重新排序，把最有用的顶上去，然后只取 Top-N（通常是 5-10 个）送给大模型。

### 1. 为什么需要重排？

向量的相似度是"浅层语义匹配"，有时候两个句子的向量很接近，但细看下来信息是冗余的或者不包含答案所需的关键细节。

更重要的是：**大模型的上下文窗口是有限的**，你不可能把所有召回的文档都塞进去。重排保证塞进去的都是精品。

### 2. 两种主流重排模式

**模式一：基于 embedding 的二次打分**

用更强的 embedding 模型（比如比索引阶段更高级的模型）重新计算问题和候选文档的相似度。速度较快，但本质上还是在向量空间里打转。

**模式二：基于交叉编码器（Cross-Encoder）的精排**

把问题和文档拼在一起，送入一个专门的 Transformer 模型进行联合编码，直接输出一个相关性分数（0-1 或 0-10）。

Cross-Encoder 能捕捉 query 和 doc 之间的交互信号，精度显著高于向量检索。代价是计算量大、速度慢。

> 这就是 RAG 里常见的 **"双塔召回 + 单塔重排"** 架构：双塔负责快，单塔负责准。

### 3. 实操建议

- 召回阶段多取一些（100 个），重排阶段只取前 5-10 个
- 重排模型推荐：bge-reranker、Cohere Rerank、Jina Reranker
- 重排的 latency 通常是整个 RAG 链路的瓶颈，注意设置超时

## 五、生成 —— AI 开始"开卷答题"

重排后的文档块 + 用户的原始问题，一起拼接成 Prompt，喂给大模型生成最终答案。

### 1. Prompt 工程

典型的 RAG Prompt 模板：

```text
你是一个专业的客服助手。请基于以下参考资料回答用户的问题。

参考资料：
{context}

用户问题：{question}

注意事项：
1. 如果参考资料中没有相关信息，请明确告知用户"抱歉，我没有找到相关信息"
2. 引用参考资料时请注明来源
3. 不要编造信息
```

**关键点：**

- **明确边界：** 告诉模型"不知道就说不知道"，这是防止幻觉最重要的护栏
- **引用来源：** 强制要求模型引用，方便溯源
- **控制长度：** 限制输出长度，防止废话连篇

### 2. 上下文窗口管理

如果重排后的文档块总长度超过了大模型的上下文限制（比如 8K 或 128K），需要做上下文压缩：

- **精简策略：** 用一个小模型对每个文档块做摘要或提取关键句
- **渐进式填充：** 按照重排分数从高到低依次填入，直到填满上下文窗口为止

### 3. 生成参数调优

| 参数        | 推荐值  | 原因                                 |
| ----------- | ------- | ------------------------------------ |
| Temperature | 0.1-0.3 | RAG 任务追求精准，不需要太多"创造力" |
| Top-P       | 保守值  | 同上，减少随机性                     |
| Streaming   | 开启    | 流式输出，用户体验更好               |

### 4. 引用标注（进阶）

让模型在生成答案时，对每一句话标注来源文档编号。例如：

> 根据公司考勤制度（来源：员工手册第 3 章），事假需要提前 3 个工作日申请……

这样用户能验证信息的真实性，也能倒逼模型减少幻觉——模型知道你要查证，就不敢乱编了。

## 六、完整调用流程串讲

假设用户问："公司年假可以累积到下一年吗？"

| 步骤          | 动作                                | 说明                              |
| ------------- | ----------------------------------- | --------------------------------- |
| ① Embedding   | 把问题转成向量                      | 使用与索引阶段相同的模型          |
| ② 召回        | 在向量库里检索 Top-100 相关文档块   | 找到员工手册里关于年假的章节      |
| ③ 重排        | 用 Cross-Encoder 精排，挑出 Top-5   | 把真正回答问题的内容顶上来        |
| ④ 组装 Prompt | 把这 5 块内容 + 问题 + 系统指令拼接 | 按重排分数从高到低排列            |
| ⑤ LLM 生成    | 大模型基于资料生成回答              | "根据《员工手册》第四章第 2 条……" |
| ⑥ 输出        | 返回给用户                          | 附上引用来源                      |

全程耗时通常在 **1-3 秒**（取决于 embedding 维度、重排模型大小、LLM 生成速度）。

## 七、那些没人告诉你但至关重要的细节

### 1. 文档版本管理

企业知识库是动态更新的。删除旧文档、更新新文档时，向量库里的旧向量必须同步删除或更新。否则用户问"最新制度"时，可能同时检索到新旧两个版本，模型会混淆。

### 2. 过滤与预筛选

不是所有文档块都该被检索。比如：

- **权限过滤：** 普通员工不该搜到"高管薪酬"相关文档
- **时间过滤：** 只检索近 3 年的文档
- **类别过滤：** 用户指定"只看客服 FAQ"

这些元数据过滤应该在向量检索之前或同时进行，减少无效检索。

### 3. 缓存

高频问题（比如"公司 wifi 密码是什么"）每次都跑完整 RAG 流程太浪费。建一层 Redis 缓存，相同问题直接返回历史答案，秒级响应。

### 4. 评估

没有评估的 RAG 系统就是盲人摸象。关键指标：

| 维度     | 指标                           | 含义                         |
| -------- | ------------------------------ | ---------------------------- |
| 检索质量 | Hit Rate、MRR、NDCG            | 相关内容是否被成功召回       |
| 生成质量 | Faithfulness、Answer Relevance | 答案是否忠实于文档、是否切题 |
| 端到端   | RAGAS 等框架自动化评估         | 全链路效果衡量               |
