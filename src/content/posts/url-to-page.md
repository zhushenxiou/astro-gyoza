## 一、总览：一次页面加载经历了什么

**一句话概括：你在地址栏输入 URL 回车，浏览器先把"要什么资源"的网络请求发出去（DNS 解析 → 建立连接 → 发送请求 → 拿到响应），再把拿回来的 HTML/CSS/JS 加工渲染成你看到的页面（解析 → 构建渲染树 → 布局 → 绘制），整个过程像一条流水线。**

用最简单的语言串一遍完整流程：

1. **输入与解析 URL** —— 浏览器先搞清你要访问的协议、域名、路径。
2. **DNS 解析** —— 把域名翻译成服务器的 IP 地址。
3. **建立连接** —— TCP 三次握手建立可靠通道；HTTPS 还要再做一次 TLS 握手加密协商。
4. **发送请求、接收响应** —— 浏览器发出 HTTP 请求，服务器返回 HTML 文档（以及后续的 CSS/JS/图片等子资源）。
5. **解析构建** —— 浏览器把 HTML 解析成 DOM 树，把 CSS 解析成 CSSOM。
6. **渲染** —— DOM + CSSOM 合并成渲染树，计算位置尺寸（布局），再绘制、合成，最终显示在屏幕上。

下面按时间顺序逐环节拆解。

## 二、网络请求线：从 URL 到拿到资源

### 1. URL 解析：先搞清楚你要什么

用户输入后，浏览器先做**安全检查与规范解析**：

- 判断输入是搜索关键字还是合法 URL，决定是去搜索引擎还是直接访问。
- 规范化 URL：补全协议（`http:`）、处理大小写、合并路径中的 `.` 和 `..` 等。
- 解析出五个组成部分：**协议、主机名、端口、路径、查询参数**。

```text
https://example.com:443/posts/1?page=2#comment
│      │              │   │      │      └─ Fragment（片段，不发送给服务器）
│      │              │   │      └─ Query（查询参数）
│      │              │   └─ Path（路径）
│      │              └─ Port（端口，默认 443）
│      └─ Host（主机名）
└─ Scheme（协议）
```

**前端视角的重点：**

- **Fragment（`#` 后面的部分）不会发送给服务器**，只用于页面内定位。
- 地址栏输入支持「智能省略」：浏览器会自动补全 `https://`，但这只是展示层的简化。

### 2. DNS 解析：把域名翻译成 IP 地址

互联网上定位一台服务器靠的是 **IP 地址**（如 `93.184.216.34`），而人记不住 IP，只记得住域名。DNS（Domain Name System）就是"电话簿"。

解析顺序（**浏览器缓存 → 系统缓存 → 路由器缓存 → 递归查询根服务器/顶级域/权威服务器**）：

```text
浏览器 DNS 缓存
   └─ 未命中 → 操作系统 hosts 文件 / 系统 DNS 缓存
        └─ 未命中 → 本地 DNS 服务器（递归查询）
             └─ 根服务器 → .com 顶级域服务器 → 权威 DNS 服务器
```

- 命中缓存：通常 **0-1ms**，几乎是瞬间。
- 完整递归查询：通常 **20-120ms**，一次全量解析动辄经历多次网络往返。

**前端视角的优化手段：**

- `preconnect`：提前建立 DNS 解析 + TCP 连接，减少首屏关键资源的等待。
- `prefetch`/`dns-prefetch`：提前解析未来会用到的域名。
- 减少跨域域名数量 = 减少 DNS 查询次数（但也别过度合并，浏览器有并发连接上限）。

### 3. TCP 连接：三次握手建立可靠通道

拿到 IP 后，浏览器与服务器建立 TCP 连接。TCP 是**可靠的、面向连接的**传输协议，建立连接需要**三次握手**：

```text
客户端                             服务器
  │ ── ① SYN (seq=x) ──────────→  │  客户端：我要建立连接
  │ ←── ② SYN+ACK (seq=y, ack=x+1) │  服务器：收到，我准备好了
  │ ── ③ ACK (ack=y+1) ────────→  │  客户端：收到，开始传输
```

**为什么不是两次？** 防止"失效的连接请求"突然又传到服务器，导致服务器白白建立一条无效连接、浪费资源。三次握手保证双方都确认"我能发、你也能收"。

**前端视角的重点：**

- **TCP 连接是可以复用的**。HTTP/1.1 的 `Keep-Alive` 和 HTTP/2 的连接多路复用，让后续请求免去重复握手的开销——这也是为什么页面加载很快的"秘密"之一。
- 浏览器对同一域名有**并发连接上限**（HTTP/1.1 通常是 6 个左右），资源太多时会排队等待。

### 4. TLS 握手：HTTPS 的加密协商（可选但几乎必有）

如果是 HTTPS，在 TCP 之上还要做 **TLS 握手**，协商加密算法、交换密钥、验证服务器证书。整个过程大致是：

```text
客户端                            服务器
  │ ── ClientHello（支持的算法）──→  │
  │ ←─ ServerHello + 证书 + 公钥 ──  │
  │ 校验证书（CA 签名链 / 有效期 / 域名）
  │ ── 生成预主密钥，用公钥加密发送 →  │
  │ ←── 双方派生会话密钥 ──────────→  │
  │ 双方都发送 Finished 确认握手完成 │
```

- 一次 TLS 握手通常增加 **1-2 个 RTT**（往返时延），对首屏影响明显。
- **TLS 1.3** 将握手压缩到 1 个 RTT，大幅提速。

**前端视角：** 用 `HSTS`（强制 HTTPS）、复用 TLS 会话（`TLS Session Resumption`）、提前 `preconnect`，都能减少握手成本。

### 5. 发送 HTTP 请求

连接建立后，浏览器构造 HTTP 请求报文并发送：

```http
GET /posts/1?page=2 HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Accept: text/html,application/xhtml+xml,...
Accept-Encoding: gzip, deflate, br
Cookie: session_id=abc123
```

**前端视角的重点：**

- `Cookie` 自动携带，是会话维持的基础，但也意味着**跨域请求要处理凭证策略**（`credentials`）。
- 请求头里的 `Accept-Encoding` 决定了服务器能不能给你**压缩后**的资源——gzip/brotli 压缩往往能让 HTML/CSS/JS 体积减少 60%-80%。

### 6. 服务器响应

服务器返回响应报文，核心是**状态码 + 响应头 + 响应体**：

| 状态码 | 含义                                       | 前端要做什么                                                     |
| ------ | ------------------------------------------ | ---------------------------------------------------------------- |
| 2xx    | 成功（200 OK / 204）                       | 正常处理                                                         |
| 3xx    | 重定向（301 永久 / 302 临时 / 304 未修改） | 301/302 跟随 `Location` 跳转；**304 直接用本地缓存**，不发新资源 |
| 4xx    | 客户端错误（404 / 403 / 429）              | 展示错误页，429 需做限流退避                                     |
| 5xx    | 服务器错误（500 / 502 / 503）              | 重试或降级展示                                                   |

**前端视角的重点：**

- **304 + 强缓存**是"减少请求"的核心：浏览器先查缓存，`Cache-Control` 判断要不要重新请求，`ETag`/`Last-Modified` 做协商。
- 响应头里的 `Set-Cookie`、`Access-Control-Allow-Origin`（CORS）、`Content-Security-Policy` 等，都直接影响前端行为。

## 三、浏览器渲染线：从字节到像素

拿到 HTML 后，真正精彩的部分才开始。浏览器的工作可以概括为下图：

```text
字节(Bytes) → 字符(Chars) → 令牌(Tokens) → 节点(Nodes) → DOM 树
                                                                │
HTML 字节流 ──► 字符解码 ──► 词法分析(Tokenizer) ──► 语法解析(Parser) ──► DOM Tree
                                                                │
CSS 字节流 ──► 字符解码 ──► 词法分析 ──► 语法解析 ──► Style Rules ──► CSSOM
                                                                │
                                            合并（Render Tree 构建）
                                                                │
                                         Layout（布局/回流）
                                                                │
                                         Paint（绘制）
                                                                │
                                         Composite（合成）
```

### 1. 解析 HTML，构建 DOM 树

HTML 被逐步解析成 **DOM（Document Object Model）树**。解析过程中遇到 `<link>`、`<script>`、`<img>` 等会触发**子资源请求**。

**关键机制：预加载扫描器（Preload Scanner）**

- 浏览器并不会傻等着解析完再请求，它有一个**预加载扫描器**，一边解析一边把 CSS、JS、图片的请求尽早发出去。
- 这也是为什么 `<head>` 里的 `<link rel="stylesheet">` 能尽早开始下载。

### 2. 解析 CSS，构建 CSSOM

CSS 解析成 **CSSOM（CSS Object Model）**，它记录了每条规则匹配的元素以及继承关系。

**前端视角的关键知识点：**

- **CSS 解析是阻塞渲染的**（render-blocking）：CSSOM 没构建完，页面就无法渲染。因为 CSS 可能改变布局，浏览器必须"等到样式齐了再画"。
- **CSS 是"向下"解析的**：元素找到自己的所有样式规则，需要把选择器匹配到 DOM 上。**选择器越复杂，匹配成本越高**——`div > p a` 比 `.foo` 慢得多。
- `@import` 会串行阻塞后续资源加载，性能差，**尽量别用**。

### 3. 构建渲染树（Render Tree）

DOM 树 + CSSOM 合并成 **Render Tree（渲染树）**，只包含**可见元素**：

- 排除 `display: none` 的元素（不占据布局空间，也不渲染）。
- 保留 `visibility: hidden` 的元素（占据空间但不可见）。

> 注意区分：`display: none` 不进渲染树；`opacity: 0` 和 `visibility: hidden` 会进渲染树。这三者对性能的影响也完全不同（见下文"优化"部分）。

### 4. 布局（Layout / Reflow）

渲染树中的每个节点，要根据视口尺寸计算**精确的位置和大小**：盒模型、边距、定位、flex/grid 布局计算……这一步叫 **Layout（布局）**，也叫 **Reflow（回流）**。

**前端视角的关键知识点：**

- 布局是**全局性**的：一个元素的尺寸变化可能引起整个文档的重新布局。
- 读写布局属性（`offsetWidth`、`getBoundingClientRect` 等）会**强制触发同步布局**，造成性能抖动。
- 现代浏览器会**批量执行**布局更新（batch/lazy layout），但你强行读取布局属性就会打断这个批处理。

### 5. 绘制（Paint）与合成（Composite）

- **Paint（绘制）**：把布局结果画出来，填充颜色、绘制边框、渲染文本，把每个元素画到对应的"图层"（Layer）上。
- **Composite（合成）**：浏览器把各个图层按 z-order 拼合成最终页面，交给 GPU 显示。

**前端视角的关键知识点：**

- **合成阶段在 GPU 上完成**，不需要重走布局和绘制。能用**合成器属性**（`transform`、`opacity`）实现的动画，性能远好于动画 `width`/`top`/`left` 等触发布局的属性。

```css
/* 性能好：只触发合成 */
.element {
  transform: translateX(100px);
  opacity: 0.5;
}

/* 性能差：触发重排 + 重绘 */
.element {
  left: 100px;
}
```

## 四、JavaScript 的"捣乱"与防阻塞

HTML 解析到 `<script>` 时会遇到大麻烦：

- 普通 `<script>` 是**同步阻塞**的：遇到它，**HTML 解析暂停**，先去下载并执行 JS，执行完才继续解析。
- `<script src="...">` 没有 `async`/`defer` 时，**下载和执行都会阻塞** HTML 解析。

三种引入方式对比：

| 方式            | 下载时机               | 执行时机                                      | 是否阻塞解析             |
| --------------- | ---------------------- | --------------------------------------------- | ------------------------ |
| 默认 `<script>` | 遇到标签时             | 立即执行                                      | **是**                   |
| `defer`         | 遇到标签时（并行下载） | DOM 解析完成后、`DOMContentLoaded` 前按序执行 | 否                       |
| `async`         | 遇到标签时（并行下载） | 下载完成立即执行（乱序）                      | 否（但执行可能打断渲染） |

```html
<script defer src="a.js"></script>
<!-- 并行下载，解析完再按序执行 -->
<script async src="b.js"></script>
<!-- 并行下载，下载完就执行 -->
```

**前端视角的结论：**

- **JS 应该放 `<body>` 底部或用 `defer`**，避免阻塞首屏。
- `async` 适合**互相独立**的脚本（统计代码、广告），因为执行顺序不保证。
- **JS 修改 DOM 会重新触发布局与绘制**：`document.write` 之类的操作会让浏览器放弃已解析的部分，性能极差，应该彻底避免。

## 五、关键渲染路径（Critical Rendering Path）与优化

从拿到 HTML 到用户看到内容，中间的必经环节就叫**关键渲染路径**。优化的本质是：**让首屏像素尽早出现**。

### 1. 一图看懂优化重点

```text
关键渲染路径的优化顺序：
① 减少/延迟 JS        → 降低对 HTML 解析的阻塞
② 优先内联关键 CSS    → 尽早构建 CSSOM
③ 延迟非关键 CSS      → 用 media 属性拆出不阻塞首屏的部分
④ 预加载关键资源      → <link rel="preload" href="hero.png" as="image">
⑤ 提前建立网络连接    → <link rel="preconnect" href="https://cdn.example.com">
```

### 2. 几个高频性能指标（前端必须懂）

| 指标 | 全称                     | 含义                                   |
| ---- | ------------------------ | -------------------------------------- |
| FCP  | First Contentful Paint   | 首次绘制出内容的时间                   |
| LCP  | Largest Contentful Paint | 最大内容块绘制时间（**首屏体验核心**） |
| TTI  | Time to Interactive      | 页面可交互的时间                       |
| CLS  | Cumulative Layout Shift  | 布局偏移累积量（衡量"页面跳动"）       |

**减少布局偏移（CLS）的经典手段：**

- 给图片/视频预留尺寸（`width`/`height` 或 `aspect-ratio`）。
- 不在已有内容上方插入元素。
- 字体加载用 `font-display: swap` 并预留占位。

### 3. 重排（Reflow）与重绘（Repaint）速查表

| 操作                                      | 触发阶段    | 性能影响   |
| ----------------------------------------- | ----------- | ---------- |
| 修改 `width`/`height`/`margin`/`position` | 重排 + 重绘 | **最贵**   |
| 修改颜色/背景                             | 仅重绘      | 中等       |
| `transform`/`opacity` 动画                | 仅合成      | **最便宜** |
| 修改文本内容                              | 重排 + 重绘 | 贵         |

**减少重排的实操建议：**

- **批量改样式**：用 `class` 切换而不是一条条改 `style`。
- **脱离文档流**：需要频繁动画的元素用 `position: absolute` 或 `transform`。
- **读写分离**：避免"读布局属性 → 写样式 → 再读布局属性"的交替操作，先读后写，让浏览器批量布局。
- **`content-visibility: auto`**：把视口外的长内容"冻结"，跳过其布局与绘制。

## 六、把整个流程串起来

以访问 `https://example.com` 为例，完整时间线：

| 阶段                | 动作                        | 大致耗时         |
| ------------------- | --------------------------- | ---------------- |
| ① URL 解析          | 规范化、安全检查            | <1ms             |
| ② DNS 解析          | 域名 → IP（命中缓存则省略） | 0-120ms          |
| ③ TCP 三次握手      | 建立可靠连接                | 1 RTT            |
| ④ TLS 握手          | 加密协商（HTTPS）           | 1-2 RTT          |
| ⑤ 发送请求          | 浏览器发 HTTP 请求          | ~1ms             |
| ⑥ 服务器处理 + 响应 | 后端计算、返回 HTML         | 数十 ms-数百 ms  |
| ⑦ 解析 HTML/CSS     | 构建 DOM + CSSOM            | 视资源量         |
| ⑧ 构建渲染树 + 布局 | 计算位置尺寸                | 视页面复杂度     |
| ⑨ 绘制 + 合成       | 输出到屏幕                  | 一帧内（16.7ms） |
| ⑩ 后续子资源 + JS   | 加载图片、脚本，JS 触发交互 | 持续加载         |

> 一次**完整**的 HTTPS 请求至少要经历 **3 个 RTT**（TCP 1 个 + TLS 1-2 个）+ DNS 时间，这还没算服务器处理时间。所以"首屏快"离不开缓存（复用连接、命中资源缓存）和预连接（preconnect/preload）。
