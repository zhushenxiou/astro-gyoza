## 一、问题：Agent 的上下文为什么总是"不够用"？

先做个类比。大模型的上下文窗口（Context Window）就像人的**工作记忆**——你能同时记住的东西是有限的，但你要处理的事情可能远远超出这个量。

普通聊天还好，写个文案、翻译段文字，几轮对话就结束了。但 Agent 不一样，它有四个"吃内存"的怪兽：

- **多轮对话本身**：任务越长，历史越多，token 指数级增长
- **工具返回结果**：一次 `curl` 可能返回 10 万字符的 JSON，数据库查询可能吐几万行
- **RAG 检索结果**：为了回答一个问题，可能要带进去好几篇文档
- **代码 / 文件内容**：Agent 读文件、跑测试，文件内容几乎原样进入上下文

于是很快你就撞上三堵墙：

### 1. 成本墙

Token 是按量计费的，上下文越长，每次请求越贵。一个 8 轮对话的 Agent 任务，可能 70% 的 token 都花在"重复发送历史"上。

### 2. 延迟墙

大模型处理输入是**自回归**的，上下文越长，首字延迟越高。用户等一个 2 分钟的回复，一半时间花在"重新读历史"上。

### 3. 遗忘墙

这是最隐蔽也最致命的一堵墙。论文《Lost in the Middle》早就指出：**模型对长上下文中间部分的内容记忆最差**。上下文拉到几万 token 时，中间那些关键指令、用户偏好、任务目标，模型可能根本没"看见"。

## 二、最粗暴的解法：直接截断

先看最朴素、成本最低的方案——**截断**。

逻辑很简单：上下文装不下了，就把最旧的内容丢掉，只保留最近 N 轮对话（所以也叫**滑动窗口**，Sliding Window）。

```python
# 伪代码：保留最近 10 轮
def build_context(history, window=10):
    recent = history[-window:]
    return "\n".join(str(turn) for turn in recent)
```

**优点：**

- 实现几乎为零，一行代码搞定
- 零额外延迟、零额外成本
- 对"单轮为主"的任务完全够用

**缺点：**

- 早期信息**永久丢失**——尤其是任务目标和用户偏好这类最前面的内容
- 用户在第 2 轮说"记住，老板的咖啡要加两份糖"，第 8 轮问"我老板的咖啡怎么点"——对不起，早被挤掉了

> 截断适合"短命"任务。任务一长，它就变成"扔笔记"而不是"记笔记"。

## 三、四大压缩流派全景

既然截断太粗暴，业界演化出了四大流派。它们不是互斥的，实际工程里往往是组合使用。

### 流派一：摘要派（Summarization）

核心思想：**把早期对话压缩成一段摘要**，而不是直接扔掉。

这就是最经典的 **Running Summary**（滚动摘要）模式：

```
[摘要] 用户正在开发一个记账应用，技术栈是 Vue3 + TypeScript，
       需求包括：多账户、分类统计、导出 Excel，后端已选定 Node.js。

[最近对话] （完整保留，作为当前工作区）
```

**怎么实现：**

```python
def maybe_summarize(messages, token_count, threshold=3000):
    if token_count > threshold:
        old_messages = messages[:-recent_size]
        summary = llm.summarize(old_messages, current_summary)
        # 用新摘要替换掉旧消息
        return [{"role": "system", "content": summary}] + messages[-recent_size:]
    return messages
```

**优点：** 信息密度高，成本极低，一次摘要能"顶替"掉几万 token。

**缺点：**

- **有损压缩**。细节（具体数字、代码片段、报错原文）几乎必然丢失
- **摘要会失真**。摘要模型可能把"用户说"转述成"用户确认"，一次抽象就是一次信息污染
- 摘要本身也可能**幻觉**——它编造了原文没有的内容

### 流派二：检索派（Retrieval-based Memory）

核心思想：**历史一条不删，全部落盘，需要时再捞回来。**

这其实就是把 Agent 的记忆做成了"外置硬盘"：

- 全量对话存入数据库（SQLite 就够）或向量库
- 每次对话前，先用当前问题去**检索相关历史**，只把命中的片段带进上下文

更进一步，业界把记忆分成两层：

| 记忆层   | 容量 | 特点                       | 实现                    |
| -------- | ---- | -------------------------- | ----------------------- |
| 短时记忆 | 小   | 当前任务的工作区，速度优先 | 就在上下文的 recent 区  |
| 长时记忆 | 大   | 跨会话的用户画像、项目背景 | SQLite / 向量库 / Redis |

**优点：**

- 细节**不丢**，随时可按需取回
- 天然支持跨会话持久化——用户下次来，Agent 还记得"上次我们聊到哪了"

**缺点：**

- 引入检索系统，有**召回率问题**——该捞的没捞回来，等于失忆
- 检索本身有延迟和成本
- 需要设计"什么时候写、什么时候读、怎么写摘要入库"的复杂策略

> 检索派和摘要派可以互补：**摘要管"大方向"，检索管"精确细节"。**

### 流派三：压缩派（Prompt Compression）

核心思想：**在 token 层面直接压缩 prompt**，用一个小模型逐 token 打分，保留信息量高的 token，删掉"嗯、啊、你你你"这类冗余。

代表工作就是 **LLMLingua** 系列（LLMLingua / LongLLMLingua / LLMLingua-2）。它的思路是：

1. 用一个小语言模型（如 GPT-2、TinyBERT）给 prompt 里的每个 token 打分
2. 打分反映"这个 token 被大模型正确预测的概率"——概率越低越"意外"，信息量越大
3. 按预算删掉冗余 token，把压缩后的 prompt 再喂给大模型

```
原始：今天天气怎么样？我打算下午出去逛街，如果下雨的话就不去了。
压缩：今天天气？下午逛街，下雨不去。
```

还有更激进的**软压缩**：不删 token，而是直接修改 attention mask，让模型"无视"冗余 token。好处是梯度可导、可端到端训练，坏处是工程复杂度高，只在研究场景常见。

**优点：**

- 压缩比高（LLMLingua 声称能到 20 倍）
- 配置灵活，可以设定压缩预算
- 对"一次性超长输入"（如塞进一份长文档）效果显著

**缺点：**

- 引入额外模型，有延迟和成本
- 对**中文和代码**的压缩效果明显打折——中文的信息密度本来就高，代码删错一个 token 语法就崩了
- 商业模型调用场景用得少，多为开源自部署的玩法

### 流派四：结构化派（Extraction / Abstraction）

最后补一个常被忽略、但工程上性价比最高的流派：**把"对话压缩"换成"状态提取"**。

与其让模型"记住说了什么"，不如直接问它"现在需要记住什么"：

```
用户：帮我把发票 20260815-001 标记为已报销，金额 1280 元。
系统指令：从本轮对话中提取需要持久化的状态，格式化为 JSON。
提取结果：{"invoice": "20260815-001", "status": "已报销", "amount": 1280}
```

然后只把这份结构化状态（而不是原始对话）存进记忆。Agent 的上下文里，**对话可以丢掉，状态不能丢**。

**优点：** 压缩比极高、信息零歧义、方便落库和程序化处理。
**缺点：** 需要为每个任务设计状态 schema，通用性不如摘要派。

### 流派横向对比

把前面几种思路放到一张表里横向对比，选型时一目了然（截断虽然不是独立流派，但作为最基础的兜底方案一并列入）：

| 流派        | 核心思路                | 压缩比 | 信息损失 | 额外开销        | 典型场景             |
| ----------- | ----------------------- | ------ | -------- | --------------- | -------------------- |
| 截断 / 滑窗 | 只留最近 N 轮           | 高     | 大       | 几乎为零        | 短对话兜底           |
| 摘要派      | 旧历史压成滚动摘要      | 高     | 中       | 摘要的 LLM 调用 | 长会话保大方向       |
| 检索派      | 全量落盘、按需捞回      | 中     | 低       | 向量库 + 检索   | 跨会话记忆、细节优先 |
| 压缩派      | 小模型逐 token 打分裁剪 | 极高   | 中       | 额外小模型      | 一次性超长文档       |
| 结构化派    | 提取状态 JSON           | 极高   | 极低*    | 需设计 schema   | 多轮工作流、状态明确 |

> *结构化派的"极低"建立在 schema 设计得当的前提下——该提取的字段一个不漏。设计漏了，信息照样丢。

一句话总结：**截断省心、摘要省 token、检索保细节、压缩极苛刻、结构化最精准。** 实战中先用结构性手段把状态和工具输出管好，再按需叠加摘要与检索，比一上来就上模型压缩靠谱得多。

## 四、工程上的组合拳：分层记忆

单独用任何一派都不够稳。实际生产中最流行的方案是**"三层上下文体"**：

```
┌───────────────────────────────────────────────┐
│  Layer 0  System Prompt（永不清除）           │
│  角色、任务目标、规则、安全边界                │
├───────────────────────────────────────────────┤
│  Layer 1  Recent Window（最近 N 轮，完整保留）│
│  临时变量、最新指令、当前工作区的"工作记忆"    │
├───────────────────────────────────────────────┤
│  Layer 2  压缩区（更早的内容）                │
│  滚动摘要 + 长时记忆检索结果                   │
│  来自向量库 / SQLite，按需注入                 │
└───────────────────────────────────────────────┘
```

**组装规则一句话：System 不动，Recent 全留，过去的进压缩区。**

### 关键决策一：压缩触发时机

压缩不是"满了才压"，而是要有明确的策略：

| 阈值       | 含义                   | 动作                             |
| ---------- | ---------------------- | -------------------------------- |
| 软阈值     | 比如 60% 窗口          | 触发一次摘要，把最旧的部分压掉   |
| 硬阈值     | 比如 90% 窗口          | 强制裁剪，保证生成阶段有空间     |
| 空闲期触发 | 每轮对话结束后异步检查 | 不影响主链路延迟，后台悄悄做压缩 |

**重要：阈值要留足"生成余量"。** 别把窗口填到 100% 再去压缩，你还要给模型的输出和工具返回留空间。

### 关键决策二：摘要的粒度

摘要不一定要一次把旧历史"全文压成一段"。更精细的做法是**按主题分桶**：

- 任务背景 → 一段
- 用户偏好 → 一段
- 已完成动作 → 一段
- 待办事项 → 一段

这样当用户问"我还有什么没做完"时，Agent 能精准定位到"待办"那一桶，而不是在一坨混合摘要里大海捞针。

### 现成实现

- **LangChain**：`ConversationSummaryBufferMemory` 是"摘要 + 窗口"组合的经典实现
- **LangMem / Mem0**：专门的 Agent 记忆框架，把"记忆写入 / 记忆检索"做成了标准工具
- **Claude**：提供 **Context Editing**（上下文编辑）能力，可以在请求中直接对历史消息做摘要替换，等价于官方支持的 running summary

## 五、哪些内容值得特殊对待

压缩不能一视同仁，有几类内容要么是"内存杀手"，要么是"碰不得的红线"。

### 1. 工具输出：头号内存杀手

Agent 的最大浪费往往来自工具返回的原始输出。处理策略：

- **结构化提取**：命令输出 / API 返回只保留关键字段，其余丢掉
- **首尾截断**：超长输出只保留头部 + 尾部（日志类的报错通常头尾最有信息量）
- **结果索引化**：完整输出写文件，上下文里只放"结果已保存到 /tmp/out.json"

### 2. 代码 / 文件：按需注入

千万不要把整个文件灌进上下文。正确姿势是：

- 用 grep / AST 抽取**相关函数**，只注入相关片段
- 报错信息给完整原文，但对应的源代码只给涉及的行
- 大文件给目录结构 + 关键片段，需要时再二次读取

### 3. 系统提示词：永远的红线

**永远不要压缩 System Prompt。** 压缩角色设定和规则会直接破坏 Agent 行为——你花一晚上调的 prompt，一次激进压缩就全毁了。

### 4. 重复内容：白白烧钱

同一份工具输出被多轮携带、同一段 RAG 片段反复注入，都是纯浪费。上下文构建前先**去重**。

## 六、压缩的代价与评估

压缩本质是"用信息损失换成本"。别光盯着压缩比，还要盯住这些指标：

| 指标       | 含义                               | 怎么测                |
| ---------- | ---------------------------------- | --------------------- |
| 压缩比     | 压缩前后 token 之比                | 直接数 token          |
| 信息保留率 | 关键信息在压缩后是否还在           | 人工抽查 / 让模型比对 |
| 任务成功率 | 同一批任务在压缩前后完成率是否下降 | 跑一套 eval 用例      |
| 忠实度     | 压缩后的摘要 / 状态是否忠于原文    | 逐条比对，防摘要幻觉  |

### 最常见的几个坑

**坑一：摘要幻觉。** 摘要模型编造了原文没有的信息，Agent 拿着假"记忆"干活。

**坑二：摘要失真。** 把"用户建议"转述成"用户要求"，把"未确认"转述成"已确认"。一次抽象一次污染，多轮下来真相已经面目全非。

> 对策：摘要系统提示里强制要求"只转述，不推断；不确定就标注不确定"。

**坑三：压缩时机不对。** 用户刚说完的重要指令，正好在压缩窗口边缘被压掉。触发阈值 + 内容重要性判断要结合。

**坑四：检索覆盖不全。** 长时记忆进了向量库，但检索时召回率低，Agent 等于选择性失忆。记忆检索要配合关键词兜底（BM25 混合召回，和 RAG 一个道理）。

## 七、选型建议：不同场景用不同打法

| 场景                       | 推荐方案                    | 原因                             |
| -------------------------- | --------------------------- | -------------------------------- |
| 客服机器人（短对话为主）   | 滑动窗口                    | 任务短，简单够用                 |
| 编程助手（长任务、多文件） | 结构化提取 + 按需注入       | 代码要精准，摘要派救不了语法错误 |
| 研究分析 Agent（长会话）   | 滚动摘要 + 长时记忆检索     | 既要大方向稳定，又要细节可查     |
| 多轮工作流（有明确状态）   | 状态提取 + 落库             | 对话可丢，状态不可丢             |
| 一次性超长文档处理         | LLMLingua 类 prompt 压缩    | 非交互场景，延迟成本可接受       |
| 通用 Agent 框架            | 三层上下文体 + 后台异步压缩 | 全都要一点，稳健为优先           |

一条经验法则：**能用结构解决的事，别用模型解决。** 很多"上下文问题"的根因是设计问题——状态该落库的没落库、工具输出该裁剪的没裁剪、该去重的没去重。先把这些做对，往往根本不需要复杂的压缩方案。
