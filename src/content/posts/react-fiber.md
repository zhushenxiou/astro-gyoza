## 一、为什么需要 Fiber？

在 Fiber 出现之前，React 的协调（Reconciliation）使用**递归**方式遍历组件树：深度优先、一次性执行到底，无法中途暂停。

> React 16 之前的架构被称为 **Stack Reconciler**——因为递归调用本身依赖调用栈，一旦开始就不能被打断。

**痛点**：只要触发一次更新，整个组件树的 diff 和 DOM 操作会一次性占满主线程。如果树很大或更新频繁，用户输入、滚动、动画都会被阻塞，表现为明显的卡顿掉帧。

**Fiber 的核心目标**：把渲染拆成一个个可以**暂停、让位、恢复**的小工作单元（Unit of Work），让浏览器可以随时插队处理更高优先级的事情（如用户点击）。

---

## 二、Fiber 节点：用链表代替调用栈

Fiber 本质上是一个**普通的 JavaScript 对象**，一个组件对应一个 Fiber 节点：

```javascript
const fiber = {
  type: 'div', // 节点类型（元素、函数组件、类组件…）
  key: null, // 复用用的 key
  stateNode: divEl, // 对应的真实 DOM / 组件实例
  props: { className: 'x' }, // 本次更新的 props
  memoizedState: null, // 状态（也是 Hooks 链表的头指针）

  return: parentFiber, // 父节点（串联方向）
  child: firstChild, // 第一个子节点
  sibling: nextSibling, // 下一个兄弟节点

  flags: Update, // 副作用标记（插入 / 更新 / 删除…）
  alternate: null, // 双缓存树中对应的另一个节点
  lanes: 1, // 优先级
}
```

**为什么用链表？** 递归依赖函数调用栈，栈的调用轨迹无法被暂停和恢复。而链表用 `return / child / sibling` 三个指针记录了遍历进度——**中断后可以从上一次停留的节点继续**，这是可中断渲染的物理基础。

遍历方式仍是"深度优先、先子后弟"，只是把隐式的调用栈变成了显式的链表。

## 三、双缓存：current 与 workInProgress

React 同时维护**两棵 Fiber 树**：

| 树               | 含义                             |
| ---------------- | -------------------------------- |
| `current`        | 当前屏幕上正在展示的树           |
| `workInProgress` | 在内存中正在构建的新树（不可见） |

- 每棵树的根节点都保存着**指向另一棵树根的指针**（`root.current`）。
- 更新时，React 基于 `current` 复用节点，构建 `workInProgress`，两树通过 `alternate` 字段一一对应（克隆而来）。
- 构建**完成并 commit 后**，把 `root.current` 指向 `workInProgress`，它成为新的 `current` 树，旧的被丢弃或复用。

**好处**：构建过程完全不触碰真实 DOM，随时可丢弃重来；且节点可以直接复用（`alternate`），避免重复创建。

## 四、两大阶段：render 与 commit

Fiber 的工作被严格划分为两个阶段：

### 1. render 阶段（可中断）

- 从根节点开始遍历 `workInProgress` 树，创建 / 更新 Fiber 节点，标记副作用（`flags`）。
- 收集"有副作用的节点"，形成一条 **effect 链表**。
- **这个阶段不产生任何真实 DOM 变更**，因此可以被随时中断、让位、甚至整棵重来。

### 2. commit 阶段（不可中断）

- 拿到 render 阶段准备好的 effect 链表后，**一次性同步执行**：操作真实 DOM、调用生命周期、执行 effect。
- 一旦开始就必须一口气执行完，因为此时 DOM 已发生变更，中途停下会留下不一致的界面。

> 一句话总结：**render 阶段"算账"，可以慢慢算、随时停；commit 阶段"动手"，必须一气呵成。**

## 五、时间切片：让渲染分片让位

**时间切片（Time Slicing）** 是可中断渲染的具体实现方式：

```
循环执行工作单元 {
  如果当前帧剩余时间还够，继续下一个工作单元
  否则：
    - 让出主线程（交给浏览器渲染、处理输入、执行动画）
    - 下次空闲时从断点继续
}
```

- 每执行一个工作单元，就检查一次是否超时，超时就让位。
- 一帧约 16.7ms，React 会把一次大更新切成若干片，**每片执行一点点，然后把主线程还给浏览器**。
- 调度由 React 自研的 **Scheduler** 完成，原理是借用 `MessageChannel` 的宏任务时机来抢占空闲时间（类似 `requestIdleCallback` 的思路，但更可控、兼容性更好）。

## 六、优先级：Lane 模型

不同更新应有不同"紧急程度"——用户输入显然比数据刷新更该被优先处理。React 用二进制位组成的 **Lane** 表示优先级：

- 一个 `Lane` 是一串 31 位的二进制数，每一位代表一条车道，`lanes` 字段记录一个 Fiber 涉及的所有优先级。
- **高优先级任务可以打断低优先级任务**：比如 render 过程中来了用户点击，会丢弃当前低优先级的工作，重新从根开始调度高优先级更新（保证最终以最新状态渲染）。
- 过期任务会被"饿死"保护：低优先级任务迟迟得不到执行时，会提升其优先级，直到被执行。

React 18 的 `useTransition` 就是基于此实现的：把非紧急更新标记为低优先级，让它在空闲时慢慢渲染，不阻塞紧急的输入响应。

## 七、一次更新：完整流程

```
setState / render 触发更新
        │
        ▼
  调度器 Scheduler 安排任务（根据 Lane 排序、决定是否打断）
        │
        ▼
  render 阶段（可中断）
    ├─ 基于 current 树构建 workInProgress 树
    ├─ 逐个处理 Fiber，标记副作用
    └─ 输出 effect 链表（可被高优先级打断重来）
        │
        ▼
  commit 阶段（不可中断，一次性）
    ├─ 根据 effect 链表操作真实 DOM
    ├─ 执行 useEffect / useLayoutEffect
    └─ 切换 root.current，进入下一次更新
```

## 八、总结

| 维度     | 旧架构（Stack）    | Fiber                           |
| -------- | ------------------ | ------------------------------- |
| 遍历方式 | 递归（依赖调用栈） | 链表（可暂停恢复）              |
| 渲染     | 一次性不可中断     | 分片可中断、可让位              |
| 优先级   | 无                 | Lane 模型，高优打断低优         |
| DOM 操作 | 与计算混合         | render 只算账，commit 才动手    |
| 双缓存   | 无                 | current / workInProgress 两棵树 |

**核心收获**：Fiber 并不是什么神秘的黑魔法，它把"一次性不可分割的递归渲染"改造成"可中断、可恢复、有优先级、按时间分片的链表遍历"，从而把主线程的主动权还给浏览器——这就是 React 高性能渲染的底层保证。
